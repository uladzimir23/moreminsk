# ADR-013 — Кастомная Admin-SPA поверх PocketBase

## Контекст

[[ADR-012 PocketBase Backend + Static Rebuild]] активировал PocketBase как БД +
API + rebuild-webhook. Встроенная PB Admin UI (`/_/`) решает хранение данных, но
остаётся **технической**: коллекции, поля, фильтры, JSON-view — интерфейс для
разработчика.

Заказчик (Pavel) — не разбирается в IT. Требование триггера из ADR-012 («редактор
без git») означает **человеческий** интерфейс: список яхт → форма с понятными
полями (название, цена/час, вместимость, фото) → «Сохранить». Список заявок с
формы. Сырая PB Admin UI этому не отвечает и открывает всю внутреннюю кухню
(схема коллекций, системные настройки).

## Варианты

### A. Кастомная клиентская SPA поверх PocketBase (выбран)
- **Плюсы:** удобный UX (только нужные поля, локализованные лейблы, без
  технической кухни); PB API-rules — единственный security-гейт; статический
  экспорт admin рядом с сайтом (новый vhost `admin.more-minsk.by`); Zod-схемы
  переиспользуются из web для валидации форм — один источник правды; нет
  серверного рантайма; повторяет istok ADR-011 (единый паттерн).
- **Минусы:** нужно собрать UI (логин, формы, списки) — ~3–5 дней; поддержка
  отдельного приложения.

### B. Сырая PB Admin UI с ролью editor
- **Плюсы:** ноль кода, готово сразу; годится как временный fallback.
- **Минусы:** технический интерфейс неудобен нетехническому заказчику; видна вся
  кухня PB. Не отвечает требованию «удобная админка» — ради чего и затевалась CMS.
  **Отвергнут** (кроме роли временного fallback на период разработки SPA).

### C. Prisma + свой Node-бэкенд
- **Минусы:** PocketBase уже даёт БД + API + auth + Admin; Prisma дублирует слой
  доступа и **обходит PB-rules**, ломая security-модель; требует свой рантайм;
  противоречит «без своего backend». **Отвергнут окончательно.**

### D. Headless SaaS (Sanity/Contentful)
- **Минусы:** вендор-лок, ценник, дублирует PB. **Отвергнут** (см. ADR-012 §C).

## Решение

Выбираем **A. Кастомная клиентская SPA поверх PocketBase.**

- Отдельное приложение `admin/` в структуре монорепо ([[ADR-014 Monorepo Restructure]]).
- Стек: **Vite + React + `pocketbase` JS SDK + react-hook-form + Zod** (как istok).
- Дизайн — наш design-system (общий `shared/` слой, ADR-014); админка выглядит в
  бренде, а не «системным» скином.
- Редактор логинится через PB-авторизацию (user с ролью `editor`); CRUD идёт
  напрямую из браузера через PocketBase REST API — серверный рантайм не нужен.
- PB API-rules ограничивают `editor` только контентными коллекциями и `leads`
  (read); системные настройки PB недоступны.
- Деплой: static build `admin/` за `admin.more-minsk.by/`; PB на том же хосте —
  `admin.more-minsk.by/api/`, `/_/` (same-origin → без CORS).

### Экраны (MVP админки)
Login · Яхты (list/edit) · Услуги (list/edit) · FAQ · Сертификаты · Документы ·
**Заявки** (read-only инбокс `leads`). Contacts — как singleton-форма.

## Последствия

- Ещё один деплой-юнит (`admin/`) в CI и на сервере (vhost + certbot).
- Zod-схемы становятся общим контрактом web ↔ admin — менять структуру данных
  нужно в одном месте (`shared/`).
- На период разработки SPA заказчик при необходимости правит через PB `/_/`
  (вариант B как fallback), затем полностью переходит на SPA.
